# 開発ルール

**作成日：** 2026-04-25

---

## 1. ブランチ戦略

```
main        ← 常にデプロイ可能な状態（直push禁止）
  └── feature/xxx   ← 機能ごとに切る
  └── fix/xxx       ← バグ修正
  └── docs/xxx      ← ドキュメントのみの変更
```

**mainへの直pushは禁止。必ずブランチを切ってPRを作成する。**
ドキュメント追加・修正も`docs/xxx`ブランチを切ってPR経由で入れる。

---

## 2. コミットメッセージ

```
feat: LINEからの排泄記録を追加
fix: 排泄アラートの時間計算がずれる問題を修正
docs: DB設計書を追加
refactor: WebhookJobの処理を整理
```

---

## 3. ドキュメントルール

### 作りっぱなし・実装しっぱなしを防ぐ

実装したら必ず `docs/scrap/` に作業ログを残す。

```
docs/scrap/
└── YYYY-MM-DD_やったこと.md
```

**書く内容（雑でOK）：**
- 何を実装したか
- なぜこう設計したか
- 詰まったこととどう解決したか
- 言語化しておきたいポイント

### スクラップのテンプレート

````markdown
# テーマのタイトル

**日付：** YYYY-MM-DD
**テーマ：** 何についての議論か

---

## 決定事項まとめ
（設計・技術選定の結論を箇条書き）

## 却下した案と理由
| 案 | 却下理由 |
|---|---|

## 用語整理
（新しく出てきた概念・技術をまとめる）

---

## 言語化チェックリスト

- [ ] 項目1

  （レビュー後に回答を書き込む）

- [ ] 項目2

  （レビュー後に回答を書き込む）
````

**言語化チェックリストはレビュー時に口頭で潰し、回答をそのまま書き込む。**
チェックが終わったら `[ ]` を `[x]` に更新する。

### アウトプットの流れ

```
docs/scrap/（雑なメモ）
    ↓ 整理
Zennスクラップ（公開アウトプット）
    ↓ 言語化しておきたいポイントに絞る
~/Private/Career/（言語化できる形）
```

## 5. コーディング規約

### Rails（バックエンド）

**ロジックの置き場所**

| 処理の性質 | 置き場所 |
|---|---|
| モデルのライフサイクルに紐づく処理（作成時の初期化など） | コールバック（`after_create` 等） |
| バリデーション | モデル（コントローラーで手動チェックしない） |
| 複数モデルにまたがる複雑な処理 | Service Object（必要になってから切り出す） |

**テスト戦略**

DB を Mock で差し替えるテストは書かない。DB ごとテストする。

| レイヤー | 内容 |
|---|---|
| Model spec | バリデーション・コールバック・モデルメソッドの検証 |
| Request spec | エンドポイント全体（ルーティング→レスポンス）の検証 |

System spec（E2E）は Next.js 側で担う。Rails 側では書かない。

---

### Next.js（フロントエンド）

**TypeScript**

- `any` は使わない
- API レスポンスの型は `types/` に定義してフロント全体で共有する（ドメイン単位でファイルを分ける）
- 型アサーション（`as`）は外部データとの境界でやむを得ず使う場合に限る。使う場合はコメントで理由を書く

**コンポーネント**

- `"use client"` はクライアント状態（`useState` / イベントハンドラ）が必要なときだけ付ける。デフォルトは Server Components

---

### 共通

**コメントを書く基準**

WHY が非自明なときだけ書く。「何をしているか」はコードを読めばわかるので書かない。

## 6. ゼロ円構成の維持

新しいサービス・ライブラリを追加するときは、無料枠を超えないか確認する。

| サービス | 無料枠の注意点 |
|---|---|
| Render.com | 15分スリープあり → UptimeRobotでping |
| Supabase | 500MB・50,000行まで |
| Vercel | 個人利用は基本無料 |
| LINE Messaging API | 月1,000通まで無料 |
