## コーナー1「技術スタックのなぜ」
### ── Rails・Next.js・npmを選んだ理由

**B:** まず全体像を教えてください。まんまる柴ってどんな構成で動いているんですか？

**A:** バックエンドがRuby on Rails（API only）・フロントがNext.js・LINE連携にLIFF・データベースはPostgreSQL（Supabase）・ホスティングはRenderとVercelです。ジョブ処理にGoodJobも使っています。

**B:** 盛りだくさんですね。バックエンドをRailsにした理由から聞かせてください。

**A:** 3つ理由があります。1つ目は、学習コストが低い。プログラミングスクールでRuby/Railsを経験していたので土台があった。2つ目は、ヘルステックSaaS企業がRailsを使っているというリサーチ結果。自分が転職を目指す業界と技術を合わせた判断です。3つ目は、GoodJobを使えばPostgreSQLだけでジョブ処理が完結するというゼロ円構成が成立したこと。

**B:** GoodJob？Sidekiqじゃないの？

**A:** そこがポイントです。Sidekiqは本番で主流のジョブ処理ライブラリなんですが、Redisが別途必要でコストが増えます。GoodJobはPostgreSQLにジョブを保存するのでSupabaseの無料枠だけで完結する。家族向けの個人開発MVPにSidekiqはオーバースペックという判断です。しかも「ActiveJobのインターフェースで書く」というのが重要で、後からSidekiqに切り替えるときは設定変更だけで済む。

**B:** 将来の乗り換えコストを下げる選択なんですね。パッケージマネージャはnpmを選んだって聞きましたが、今はpnpmが主流じゃないですか？

**A:** pnpmが速くてディスク節約になるのは確かです。仕組みはこうで、npmは各プロジェクトにnode_modulesをまるごとコピーするんですが、pnpmはグローバルキャッシュに実体を1つ置いてハードリンクで参照します。複数のpackage.jsonがあるモノレポ構成なら恩恵が大きい。でもこのプロジェクトはバックエンドがRailsなので、JSのpackage.jsonはフロント側の1つだけ。pnpmのハードリンク共有が効かないので、シンプルにnpmで十分という判断です。

**B:** 規模に合わせた選択ってことですね。

## コーナー2「設計思想のなぜ」
### ── RailsはなぜDDDを選ばないのか

**B:** さて、このアプリを作るときにJavaでDDDをやっていた経験があるとのことで。RailsとDDDの違いって何ですか？

**A:** 一言で言うと「誰がデータベースに話しかけるか」の違いです。Javaで使うDDDのRepositoryパターンでは、DBへの操作は専用のRepositoryクラスが担います。ドメインオブジェクトはDBを知らない。一方RailsのActive Recordはモデル自身がDBに話しかけます。`Dog.find(1)` で犬を取ってくる、`dog.save` でINSERTする。ドメインロジックとDBロジックをあえて同じクラスに混在させる設計です。

**B:** 「あえて混ぜる」というのが面白いですね。なぜそうするんでしょう。

**A:** DHHというRailsの作者の哲学があります。「Convention over Configuration（設定より規約）」「Provide sharp knives（鋭いナイフを渡せ）」というやつです。Javaは静的型付け・アクセス修飾子・インターフェースでプログラマーを保護する言語。DHHはこれを「開発者を信頼していない」と批判した。Rubyは逆で、どのクラスにも後からメソッドを追加できるオープンクラスという仕組みがあります。これが「黒魔術」と呼ばれる由来でもあります。

**B:** ちなみにRubyで組み込みクラスにメソッドを追加するって、たとえばどんな感じですか？

**A:** たとえばこんな感じです。`class String` を開けてそこに `blank?` メソッドを追加する。すると `"".blank?` が `true` を返すようになる。Railsはこれを使って `"dog".pluralize` → `"dogs"` とか、`has_many` という関連定義マクロを実現しています。どこでメソッドが定義されているか追いにくいので「黒魔術」と言われますが、DHHは「それが表現力だ」という立場です。

**B:** なるほど。じゃあなぜこのプロジェクトでDDDを選ばなかったんですか？

**A:** 3つの理由があります。1つ目、ドメインが単純。柴犬のお世話記録なのでAggregateを切るほどの複雑さがない。2つ目、Active RecordにRepositoryを無理やり混ぜると中途半端な設計になる。3つ目、個人開発で認知負荷を増やすメリットがない。DDDは「大規模チームで誰かのコードが誰かを壊さないための構造」として機能します。信頼できる規模では複雑すぎる。

**B:** アーキテクチャの選択がテスト戦略まで決めるって聞いたんですが、どういうことですか？

**A:** これが面白いんですよ。Active RecordはドメインとDBが混在しているので「DBなし！」と言い張ることが構造的にできません。なのでRailsはDBごとテストします。Model specでバリデーション、Request specでエンドポイント全体。これはDHHが「DBごとテストする方が信頼できる」という立場だからです。DDDはRepository層が分離されているのでMockで差し替えてDBなしテストができる。アーキテクチャの選択がそのままテスト戦略を決めているわけです。

**B:** DHHが「TDD is dead」と言ったのも関係してますか？

**A:** 直結してます。2014年のRailsConfでDHHが「test-induced damage（テストに誘発される設計の歪み）」という概念を提唱しました。MockでテストするためにRepositoryを作るのは、テストのために設計を歪めているという批判です。DBごとテストすれば「本物のDBが正しく動く」という仮定ごと検証できる。Kent BeckやMartin Fowlerを巻き込んだ三者公開討論にまで発展した論争です。

## コーナー3「DB設計のなぜ」
### ── テーブル構成・外部キー・STI・ポリモーフィックアンチパターン

**B:** では次はDB設計。まず全体のテーブル構成を教えてください。

**A:** v1は6テーブルです。users（LINEユーザー）・groups（家族グループ）・group_members（中間テーブル）・dogs（犬）・care_records（お世話記録）・alert_settings（アラート設定）。

**B:** groupsとdogsを分けたのはなぜ？

**A:** 多頭飼い対応です。1グループに複数の犬がいる可能性があるので、groups → dogsを1対多にしました。分けなかった場合、2匹目が増えたときにグループ情報の複製や設計変更のコストが発生します。

**B:** group_membersが中間テーブルなのは？

**A:** usersとgroupsが多対多の関係だからです。1ユーザーが複数グループに所属できる、たとえば実家グループと嫁ぎ先グループの両方に同じユーザーが参加するケース。group_membersテーブルで橋渡しして、`(group_id, user_id)` のunique制約で二重登録を防いでいます。

**B:** 外部キー制約ってよく聞きますが、そんなに大事なんですか？

**A:** はい、大事です。外部キー制約をかけると、存在しない親レコードを参照する子レコードを作れなくなります。たとえばdogs.group_idにgroup_membersとの外部キーを貼っておくと、存在しないグループに犬を登録しようとしたらDBが弾いてくれる。別ユーザーのデータを横断して取得するリスクも防げます。CASCADEというオプションを使うと、親レコードを削除したとき子レコードを自動的に一緒に削除できます。

**B:** 外部キー制約が「貼れない」ケースもあるって聞きました。

**A:** ポリモーフィック関連アンチパターンです。中間テーブルに `item_type`（"CareRecord" or "Post"）と `item_id` を持たせる設計があるんですが、`item_id` の参照先テーブルが `item_type` によって変わります。DBは外部キー制約を「どのテーブルのどのカラムを参照する」と固定で定義する必要があるので、これができない。結果としてCASCADEも機能せず、親レコードを削除しても子レコードが孤立して残り続けます。

**B:** じゃあタイムライン表示でケア記録と投稿（Post）を混ぜたいときはどうするんですか？

**A:** STI（Single Table Inheritance）を使います。care_recordsテーブル1つに `type` カラムを持たせて、RailsがCareRecordとPostを別クラスとして扱う設計です。1クエリでタイムラインを取得できて、Postにしか関係ないロジック（写真の保持期間制御など）をPostモデルに閉じられます。テーブルを分けるとUNIONが必要でページネーションも複雑になるので、v1ではSTIが最適です。

**B:** care_typeをenumにした理由も教えてください。

**A:** DB不整合を防ぐためです。文字列で保存すると `'toilet'`・`'Toilet'`・`'トイレ'` のようなゆらぎが起きる。enumにすることでRailsが定義した値以外を入れようとするとArgumentErrorを投げて弾いてくれます。ただしこれはRailsを経由する限りの型安全で、生SQLで直接操作するとチェックが入らない。完全な型安全のためにはDBのcheck constraintも合わせて追加します。

## コーナー4「API設計のなぜ」
### ── REST・PUT vs PATCH・JWT認証

**B:** コーナー4はAPI設計です。Rails API onlyって何が「only」なんですか？

**A:** ビューがない構成です。通常のRailsはERBというテンプレートエンジンでHTMLを返しますが、API onlyはJSONしか返しません。`rails new myapp --api` のオプション一つでビュー関連のgemやミドルウェアが省かれた軽量構成で作られます。

**B:** Railsには7つのアクションがあると聞きましたが。

**A:** RESTfulなリソース設計の標準アクションです。一覧取得（index）・1件取得（show）・作成（create）・更新（update）・削除（destroy）・作成フォーム（new）・編集フォーム（edit）の7つ。`new` と `edit` はHTMLフォームを表示するためのアクションなのでAPI onlyでは不要です。フォーム表示はNext.jsの仕事なので。

**B:** PUTとPATCHの違いって何ですか？

**A:** PUTはリソース全体を丸ごと置き換える。PATCHは変更したい部分だけ送って一部を更新する。アラート設定は `interval_hours`（アラートまでの時間）だけ変えることが多いので、PATCHが適切です。

**B:** アラート設定にPOSTが不要な理由は？

**A:** 犬を作成したタイミングで自動生成されるからです。RailsのライフサイクルフックであるActiveRecordコールバックを使っています。`after_create :create_default_alert_settings` という形でDBへのINSERTが完了した直後に走るメソッドを定義する。犬を登録したとき、自動でpeeとpoopのアラート設定が初期値（4時間）で作られます。フロントから2回APIを叩く必要がなくなる。

**B:** 認証にJWTを使っていますが、セッション認証との違いを教えてください。

**A:** 「状態を持つ場所」が違います。セッション認証はサーバー側がユーザーの状態を保持します。フロントとバックを別サーバーに分けるとセッションを共有できない。JWTはトークン自体にユーザーIDと有効期限が入っているので、サーバーが状態を持たなくてよい。RailsはJWT Secretで署名を検証するだけ。ステートレスな構成になります。

**B:** LINEのIDトークンをそのまま使い続けないのはなぜですか？

**A:** 有効期限が数分と短いからです。LIFFが取得したIDトークンをRailsで検証して、自前のJWT（有効期限を長めに設定）を発行します。以降はそのJWTをAuthorizationヘッダーに付けてAPIを叩く設計です。

## コーナー5「LINE連携のなぜ」
### ── LIFF・Webhook・非同期処理・セキュリティ

**B:** LINEを使ったアプリの設計は独特ですね。まずLIFFって何ですか？

**A:** LINE内蔵ブラウザでWebアプリを開く仕組みです。`@line/liff` というSDKをNext.jsに組み込むと、LINEログイン済みユーザーの情報（IDトークン・表示名）をほぼ自前実装なしで取得できます。LINEを離れずにNext.jsのWebアプリが表示されて、閉じるとLINEのトーク画面に戻る。

**B:** LINEミニアプリとの違いは？

**A:** 審査が要るかどうかです。ミニアプリはLINE公式プラットフォームとしての審査・承認が必要で個人開発には重い。LIFFはWebページをLINE内ブラウザで開くだけなので審査不要です。

**B:** グループチャットに入れる方式ではなく、1対1チャット方式にしたのはなぜですか？

**A:** グループチャットにBotを入れると全メッセージがWebhookに届いてしまいます。「今日どこ行く？」みたいな家族の日常会話もぜんぶサーバーに来る。フィルタ実装が必要でプライバシーも問題になる。1対1方式なら犬の記録だけが届くのでシンプルで安全です。

**B:** リッチメニューとFlex Messageって何が違いますか？

**A:** リッチメニューはトーク画面下部に常時表示されるLINE側の固定ボタンです。ボタン例は「おしっこ」「うんち」「散歩」「ごはん」「状態確認」「タイムライン」の6つ。タップ1回で記録完結、文字入力不要。Flex MessageはBotがDBから最新情報を動的に取得してカード形式で返信するものです。「最後のおしっこから何時間経った」というサマリーをカードで見せる。

**B:** 散歩だけQuick Replyがあるのはなぜ？

**A:** 散歩はショートコースとロングコースを区別したいからです。おしっこ・うんち・ごはんは「やった」という事実だけで記録が完結しますが、散歩はどちらのコースかを指定しないと記録が不完全になる。記録したい情報の数が違うので1ステップ追加しています。

**B:** 取り消し機能を実装しなかった理由は？

**A:** ソフトデリート（論理削除）のコストと、利用頻度のバランスを見た判断です。ソフトデリートは全クエリに `WHERE deleted_at IS NULL` を追加する必要があり、1箇所でも漏れると削除済みデータが表示されるバグになる。家族数人のアプリで押し間違えは低頻度なのでLIFFタイムラインからの修正で十分と判断しました。

**B:** WebhookってLINEが送ってくる側なんですよね。セキュリティはどうするんですか？

**A:** 署名検証です。`/webhooks/line` はJWT不要の公開エンドポイントなので誰でもPOSTできる状態です。そこでLINEが各リクエストにChannel Secretで生成した署名（`X-Line-Signature`）を付けて送ってきます。Railsがこれを検証してLINEからのリクエストかどうか確認します。通常のAPIと逆で「LINEが送る側・Railsが検証する側」という構造です。

**B:** Webhookの非同期処理が必要な理由は？

**A:** LINEは3秒以内に200が返らないとタイムアウト＋リトライします。RenderというホスティングサービスはFreeプランだと15分無操作でスリープして、起動に10〜30秒かかる。重い処理を同期で書くと詰まる。対策はUptimeRobotで5分おきにpingしてスリープさせないこと。GoodJobで即200を返して処理を後回しにすること。業務のJavaでジョブをキックしてHTTP 200を即返すパターンと同じ設計思想です。

## コーナー6「フロント実装のなぜ」
### ── TypeScript・shadcn/ui・モックファースト

**B:** 最後のコーナーはフロント実装です。TypeScriptの型アサーション（as）って何ですか？

**A:** 「この値はこの型だ」とTypeScriptに断言する構文です。型チェックを強制的に黙らせるもの。重要なのは「実行時には何も変換しない」点です。型のラベルを貼り替えるだけで値は元のまま動く。なので `"hello" as unknown as number` としても実行時は"hello"のままで、`x + 1` が "hello1" になるような変な値が静かに流れる。型エラーより始末が悪いので使用は最小限です。

**B:** どんなときに使っていいんですか？

**A:** TypeScriptが「わからない」が開発者は「わかっている」状況です。2つあります。1つ目はDOM操作。`getElementById` は `HTMLElement | null` を返しますが、自分でHTMLを書いているのでinputだとわかっているとき。2つ目は外部データ。fetchやJSON.parseはTypeScriptに中身がわからない。このプロジェクトで一番出てくるのはRails APIのレスポンスです。

**B:** `types/` ディレクトリは何のためにあるんですか？

**A:** APIレスポンスなど外部データの型をドメイン単位でまとめる場所です。恩恵は2つ。VS Codeの補完が効くこと。Rails側でカラム名を変えたとき、`types/` の型を更新するとフロント全体の使用箇所が一斉に赤くなってすぐ気づけること。`any` にするとこれが全部効かなくなります。

**B:** `next dev` で型エラーがあっても動いてしまうって本当ですか？

**A:** 本当です。`next dev` はSWCがJavaScriptに変換するだけで型チェックを省略します。型エラーがあっても動いてしまう。厳密な型チェックは `tsc --noEmit` を使います。

**B:** モックファースト開発って何ですか？

**A:** 本物のAPIが存在しない段階でハードコードしたダミーデータでUIを完成させる開発方針です。テストのためのMockとは別の話です。このプロジェクトはバックエンドがRails + Supabase + Render + LINE Developersという複数サービスが絡む複雑な構成なので、まずモックでフロントを完成させてから1つずつ繋いでいく。問題が起きたときフロント・バックどちらの問題か切り分けやすいのも理由です。

**B:** v0.devを採用した理由は？

**A:** shadcn/uiとの親和性です。v0.devはVercelエコシステムのツールでshadcn/uiコンポーネントを出力します。shadcn/uiはTailwindクラスがそのままコードのReactコンポーネント集で、`components/ui/` にソースコードとしてコピーされるので自分でコードを所有できます。既存のNext.js構成にそのまま組み込めます。競合のBolt.newはブラウザ上で動いて即デプロイできますがコード制御が弱い。Lovableは丸ごとアプリ生成が得意ですがコード品質が粗い。
